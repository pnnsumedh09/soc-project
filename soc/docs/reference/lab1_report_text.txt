2.1 Quantization

Symmetric quantization and asymmetric quantization are the common approaches used to
represent quantized values.

Symmetric quantization maps the floating point values to an integer range centered around
zero. It uses a scale factor to map the largest magnitude value to the available integer range.

symmetric quantization does not require a zero-point. It is commonly used for neural network
weights.

Asymmetric quantization allows the quantized range to be shifted relative to zero and so it will
have both scale and zero point. The quantization and dequantization operations are




where (z) is the zero-point. The zero-point allows the quantized range to better match the
minimum and maximum values of the original tensor. This can be useful when the values are
not distributed symmetrically around zero.

Each of these quantizations can differ in the granularity and the bit width of the values. In
per-tensor quantization, one scale is used for the entire tensor. Per-channel and per-group
quantization use separate scaling factors for smaller portions of the tensor. Finer-grained
quantization can better represent variations in the weight distribution, but requires additional
scaling information.

Common weight precisions include 2-bit, 3-bit, 4-bit, 5-bit, 6-bit, and 8-bit. Lower bit-widths
provide greater compression but come with the cost of losing accuracy. There will be a
quantization error because the actual values are reduced to less number of bits. The higher the
bit-width, the more information it will have and introduces less quantization error.

The quantized values are typically stored in blocks along with their scaling information. For
example, with 4-bit quantization, two 4-bit values can be packed into a single byte. During
computation, the packed values are extracted and combined with their corresponding scales to
approximate the original values. This allows the weights to remain compressed in memory
instead of storing the full-precision tensor.

2.2 Quantization formats in Llama.cpp

Llama.cpp supports several weight quantization formats, including Q4_0, Q5_0, Q8_0 and the
K-quant family Q2_K, Q3_K, Q4_K, Q5_K, and Q6_K. The main difference between these
formats is the number of bits allocated to the quantized weights and the block structure used to
store the associated scaling information.

The simpler _0 formats use block-wise quantization with a common scale for each block. The
K-quant formats use larger super blocks containing smaller blocks and additional scaling
information. This provides more flexibility in representing the distribution of the original weights,
particularly at lower bit-widths.

 Format           Nominal            Approx. bits/weight
                 bits/weight

  Q4_0                4                       4.5

  Q5_0                5                       5.5

  Q8_0                8                       8.5

  Q2_K                2                      ~2.6

  Q3_K                3                      ~3.4

  Q4_K                4                      ~4.5

  Q5_K                5                      ~5.5

  Q6_K                6                      ~6.6

For example, Q8_0 represents groups of 32 weights using 8-bit quantized values together with
an FP16 scale. Lower-bit formats pack the quantized values more densely and store additional
scaling information alongside them. During a matrix operation, Llama.cpp's optimized kernels
extract the packed values and apply the corresponding scales as part of the computation.

2.3 Weights, KV cache, and activations

Quantization is not applied uniformly to every tensor in the Llama.cpp computation graph. The
model weights are the primary target of quantization and can remain stored in compressed
GGUF formats such as Q4_K, Q5_K, Q6_K, or Q8_0.

The KV cache is handled separately and can use floating-point representations such as FP16,
along with other supported cache types. Intermediate activations are also not automatically
stored at the same precision as the quantized weights. Depending on the operation and
backend, intermediate tensors can use higher-precision floating-point representations.

Conceptually, the data path can be viewed as:

Quantized weights → Matrix operations → Intermediate values → Attention/KV cache →
Next layer

Therefore, a model described as Q4 or Q8 refers primarily to the representation of its weights. It
does not mean that all intermediate values throughout the computation graph are stored at the
same bit-width.

2.4 Effect of precision on accuracy

The main source of accuracy loss is the approximation introduced when floating-point values
are mapped to a limited set of quantized values. Lower bit-widths provide greater compression
but generally introduce more quantization error. Finer-grained scaling and more structured
formats can reduce this error by representing different value distributions more accurately.

Overall, quantization provides a trade-off between memory footprint, memory bandwidth, and
numerical accuracy. Higher precision retains more information but requires more memory, while
lower precision provides greater compression at the cost of increased approximation error.

2.6 Analysis of quantization benchmark results:

Throughput

We expected lower precision models to run faster due to reduced memory transfers, but Q8_0
was actually the fastest at 5.81 tok/s, followed by Q2_K at 5.61 tok/s and Q4_K_M at 5.14 tok/s.

These factors explain this throughput behavior:

   ●​ K-quant formats like Q4_K_M and Q2_K use complex block structures that require extra
      CPU bit-shifting and unpacking operations to extract weights during execution. On our
      300 MHz Cortex-A53 core, this extra arithmetic overhead is possibly the reason
      execution slows down and outweighs the time saved on memory transfers.
   ●​ Q2_K runs slightly faster than Q4_K_M because its significantly smaller model size in
      memory helps offset part of this bit-unpacking cost, placing its overall speed between
      Q8_0 and Q4_K_M.

Accuracy

In accuracy, Q4_K_M achieved a score of 54.3, Q8_0 scored 51.4, and Q2_K dropped to 48.1.

Even though Q8_0 uses higher precision, Q4_K_M has better accuracy. This is likely due to
how K-quant formats work. Instead of quantizing every layer uniformly like Q8_0, Q4_K_M uses
variable precision across different model layers to keep important tensors at higher quality,
which helps maintain overall accuracy. Small prompt-level variations in the evaluation tasks
could also be a factor.

The drop to 48.1 for Q2_K shows the limit of aggressive quantization. Squeezing weights down
to 2 bits introduces enough quantization noise to noticeably degrade model reasoning.

3.1 Optimization features overview

The Ultra96 platform has a Xilinx Zynq UltraScale+ MPSoC equipped with a quad-core ARM
Cortex-A53 processor. The primary optimization knobs are available on the hardware side of
things as well as in compiler configuration and runtime execution.

   1.​ ARM NEON Advanced SIMD Vectorization:

               The ARMv8-A architecture features dedicated 128-bit vector execution units and
       vector registers (v0–v31). In llama.cpp, matrix multiplication kernels such as
       ggml_vec_dot_q8_0 use SIMD intrinsics to process multiple 8-bit integer operations
       concurrently per instruction instead of using scalar execution loops.

   2.​ Microarchitectural Instruction Scheduling (-mcpu=cortex-a53):

               The Cortex-A53 is an in-order, dual-issue superscalar pipeline. Directing GCC to
       target -mcpu=cortex-a53 rather than a generic baseline (-march=armv8-a)
       activates instruction scheduling tailored to the Cortex-A53’s dual-issue hazard tables and
       load-to-use latencies, reducing structural pipeline stalls.

   3.​ Multi-Core Thread Parallelism (--threads N):

              The MPSoC contains four symmetric Cortex-A53 physical cores running at up to
       1.2 GHz. At runtime, llama.cpp can partition the rows and weight tiles of tensor
       operations across independent POSIX threads mapped across the available CPU cores.

3.2. Experimental Setup: How Optimizations Were Controlled
To isolate and profile these features on the Ultra96 board using Qwen2.5-0.5B (Q8_0), three
controlled configurations were tested using benchmark.py:

   1.​ Config A (Scalar Baseline / No-NEON, 4 Threads):​
       Built on mario with -U__ARM_NEON -fno-tree-vectorize -DGGML_NEON=OFF
       -DGGML_LLAMAFILE=OFF. This forces llama.cpp to disable ARM NEON intrinsic code
       paths and suppresses GCC auto-vectorization, falling back to a scalar
       1-byte-at-a-time loop for tensor dot products while retaining 4 worker threads.
   2.​ Config B (Tuned Microarchitecture & NEON, 1 Thread):​
       Built on mario targeting -mcpu=cortex-a53 -O3 -DNDEBUG with full NEON
       vectorization enabled. Tested on the board using runtime flag --threads 1 to establish
       a single-core baseline with vectorization active.
   3.​ Config C (Tuned Microarchitecture & NEON, 4 Threads):​
       Built on mario targeting -mcpu=cortex-a53 -O3 -DNDEBUG with full NEON
       vectorization enabled. Tested on the board using runtime flag --threads 4 to assess
       full multi-core parallel scaling.

3.4 Analysis

The benchmark results highlight how vectorization and thread count drive execution speed on
the Ultra96 board. Comparing the standard baseline (5.81 tok/s) to the NONEON run (1.47
tok/s) shows that turning off ARM NEON SIMD causes a massive drop in speed, making
execution nearly 4 times slower. This proves that vector instructions are essential for processing
tensor math efficiently on this board.

Thread count also plays a major role in overall speed. Running the Cortex-A53 build on a single
thread yields only 1.72 tok/s, but scaling up to 4 threads increases speed to 5.83 tok/s (a 3.39x
parallel speedup). Adding the specific CPU compiler flag (-mcpu=cortex-a53) gives a slight
extra boost over the default toolchain baseline, pushing speed from 5.81 tok/s to 5.83 tok/s due
to better instruction scheduling. Across all four test cases, the benchmark accuracy score
remains effectively identical (~51.4 to 52.3), showing that these performance gains come with
no loss in model accuracy.

Profiling llama-cli on a single Cortex-A53 CPU core running at 300 MHz resulted in a total

Primary Bottleneck

   1.​ Quantized Vector Dot Product (ggml_vec_dot_q8_0_q8_0):

              This part was the primary bottleneck which took 89% of the compute time which
       is around 130s out of 145s. This computes dot products for 8-bit quantized integer
       tensors. Executing over 25.4 million calls on the 300 MHz CPU core makes this single
       arithmetic routine the primary performance bottleneck.

Secondary Functions (10.18% Total)

   1.​ Graph Dispatch & Attention (2.21%):

              Matrix multiplication graph dispatch (ggml_compute_forward_mul_mat) and
       FlashAttention passes (ggml_compute_forward_flash_attn_ext).

   2.​ Tokenization & Setup (2.75%):

               Vocabulary loading (llama_vocab::impl::load) and Byte-Pair Encoding string hash
       table lookups during initialization.

   3.​ Other Compute & I/O (5.22%):
             Minor vector math (ggml_vec_swiglu_f32, FP16 dot products), memory cleanup,
       and GGUF file I/O.

Overall, non-computational tasks like file I/O, string parsing, memory allocation, and tokenization
collectively account for less than 5 percent of total runtime. CPU execution time is almost
entirely consumed by low-level quantized vector math in the ggml_vec_dot_q8_0_q8_0
kernel. From our profiling results, we understood how critical accelerating this dot product
function is to overall performance. Because of this, most of our hardware acceleration efforts on
the FPGA will focus on offloading this specific routine. Once this primary bottleneck is solved,
we will look into optimizing secondary functions from the remaining 10 percent, such as matrix
multiplication dispatch and FlashAttention . We can optimize these secondary tasks on the CPU
using techniques like ARM NEON SIMD vectorization, instruction pipelining and memory layout
adjustments.
