Hardware Design and HLS Optimizations:
       The SystemC model replicates the latency, memory footprint, and exact
mathematical behavior of Vitis HLS hardware implementation specifically, the design_7
baseline from Lab 2.


   a)​ Datapath and dot_q8_0_block Implementation:

              The core mathematical logic is encapsulated within the dot_q8_0_block
      function, which represents a single iteration of the Lab 2 BLOCK_LOOP. This
      function processes one block of DOT_QK (32) int8 pairs with corresponding FP16
      scales.

             The function iterates 32 times, performing integer Multiply-Accumulate
      (MAC) operations on the xq and yq vectors, summing the results into a 32-bit
      integer (sumi). After the integer loop, sumi is cast to a float and multiplied by the
      two FP16 scales (xd and yd). To execute the dot_half_to_float conversion
      efficiently, the function uses pure integer bitwise logic, including a fixed 4-step
      leading-zero count to re-normalize denormalized numbers without data-dependent
      loop delays. The caller adds the float returned by dot_q8_0_block into a running
      sumf accumulator, preserving the exact operation order of llama.cpp to guarantee
   bit-exactness.




b)​ HLS Directives and Memory Reshaping

          The hardware targets the Zynq UltraScale+ ZU3EG FPGA with a 10 ns
   clock constraint. The Vitis HLS compiler estimated a critical path of 6.792 ns. To
   feed the 32 MAC units in dot_q8_0_block fast enough array reshaping was done
   to the BRAMs. The xq and yq BRAM arrays were restructured using a cyclic
   reshape with a factor of 8. This packs the 8-bit quantized weights into 64-bit
   BRAM words, drastically increasing the memory bandwidth available per clock
   cycle.

c)​ Pipeline Architecture and Timing

          Because of the array reshaping and Vitis HLS default optimizations, the
   dot_q8_0_block execution (BLOCK_LOOP) is heavily pipelined. The pipeline
   achieves an II of 4, meaning a new 32-element block can be fed into the datapath
   every 4 clock cycles. A single block takes 21 cycles to propagate through the
   pipeline. The SystemC thread models this pipelined execution deterministically
   using the formula:

                    cycles(nb) = startup (1) + nb * II (4) + pipeline_drain (17)

           The pipeline drain of 17 is derived by subtracting the II (4) from the
   iteration latency (21). For a maximum load of 152 blocks, the hardware guarantees
   completion in exactly 626 cycles.
   d)​ Resource Constraints and BRAM Budgeting

             The local scratchpad memory is structurally separated into four distinct
      C++ arrays (spad_xq, spad_yq, spad_xd, spad_yd) to perfectly mirror the physical
      Block RAM (BRAM) ports generated by HLS. The design is statically sized to
      handle a maximum capacity of DOT_MAX_NB = 152 blocks. This capacity
      requires exactly 10,336 bytes of local memory. The target ZU3EG FPGA contains
      216 36-Kb BRAMs (approx. 7.6 Mb). This specific design consumes only about 6
      of those BRAMs, keeping it well within the strict hardware budget. Because the
      array bounds are fixed, the TLM socket strictly rejects any bus access beyond
      these sizes, enforcing the memory budget by physical construction rather than
      runtime software checks.


High-Level Architecture (ARM - Accelerator Interface)
       The system operates across two separate OS-level processes synchronized via
communication protocol. The ARM Cortex-A53 processor runs a full PetaLinux guest
operating system inside QEMU, while the dot product accelerator's cycle-level timing
model executes in a standalone SystemC process (zynqmp_dot). The two simulators are
tied together using Xilinx's remote-port framework over a Unix-domain socket. The
simulators maintain lockstep timing ensuring simulated elapsed time remains consistent
between the Linux guest and the hardware model.
      The accelerator acts as a pure bus slave. There is no Direct Memory Access
(DMA) or bus-mastering initiator socket on the accelerator. Instead, the ARM CPU
executes load/store instructions (readl()/writel()) to copy data from main memory into the
physical addresses mapped to the Programmable Logic (PL).

        When the ARM accesses the 0xA0100000 address range, QEMU traps the MMIO
access and forwards it across the socket as a TLM-2.0 generic payload. On the SystemC
side, the iconnect bus decodes this address and routes the transaction to the
DotAccel::b_transport target socket.

       When the accelerator finishes a computation, it asserts a hardware interrupt line. In
the SystemC platform, this is wired to zynq.pl2ps_irq[5]. The remote-port framework
forwards this signal back to QEMU, where it is mapped to the ARM Generic Interrupt
Controller (GIC) as SPI 94 (GIC HWIRQ 126).


Hardware/Software Handshake Protocol
The synchronization between the ARM CPU (software driver) and the accelerator
(hardware model) follows a register-based handshake designed to prevent data
corruption.

   1.​ Data Transfer Phase: Before initiating a computation, the ARM driver writes the
       input vectors to the four local scratchpad memories (XQ, YQ, XD, YD). The TLM
       target socket adds simulated bus latency to each 32-bit word written.
   2.​ Configuration Phase: The ARM writes the number of blocks to be computed into
       the DOT_REG_NB register and writes a 1 to DOT_REG_IRQ_EN if
       interrupt-driven synchronization is desired.
   3.​ Activation (Clear & Start): The driver writes a DOT_CTRL_CLEAR command
       to the CTRL register to wipe any stale DONE or ERR states from previous runs. It
       then writes DOT_CTRL_START to the CTRL register.
   4.​ Hardware Execution:
           ○​ Upon receiving the START command, the SystemC target socket
               immediately raises the STATUS.BUSY flag and notifies start_ev.
           ○​ The compute_process thread wakes up, clamps the block count to
               DOT_MAX_NB if necessary, and executes the math logic.
           ○​ The thread utilizes wait() statements to advance the simulated time
               according to the HLS pipeline parameters (1 startup cycle, 4 cycles per
               block, 17 finish cycles).
   5.​ Completion & Synchronization: Once the wait() statements complete, the thread
       drops the BUSY flag, raises the DONE flag, and triggers irq_ev. If interrupts are
       enabled, the irq_process method asserts the physical interrupt line to wake the
       sleeping ARM processor. Alternatively, the ARM can poll the STATUS register
       waiting for DONE to go high.
   6.​ Result Retrieval: The ARM driver reads the final floating-point result from
       DOT_REG_RESULT and the elapsed hardware cycles from
       DOT_REG_CYCLES.

Protocol Safeguards
       To prevent the software from corrupting an in-flight computation, the TLM model
implements strict state-machine safeguards. If the ARM attempts to write to any
scratchpad memory, modify the NB register, or issue a new START command while the
BUSY flag is high, the hardware explicitly ignores the write. Instead of hanging the bus
or corrupting data, the hardware sets a sticky ERR bit in the STATUS register, which the
driver can detect, and logs a warning on the SystemC console.

Memory Map and Software Protocol

The integration between the ARM driver and the SystemC hardware relies on a shared C
header (dot_accel_regs.h), which defines the exact memory map, ensuring both software
and hardware always agree on memory addresses.

The accelerator's base address is 0xA0100000, mapped directly onto the AXI HPM0 FPD
window. The accelerator's overall memory footprint (DOT_WINDOW_SIZE) is 128 KB
(0x20000).

Resource Mapping The Linux driver divides this 128 KB footprint into two resources:

   1.​ Registers (Resource 0): A 256-byte (0x100) window starting at the base address
       (0xA0100000), reserved for control and status registers.
   2.​ Scratchpads (Resource 1): A 24 KB (0x6000) window starting at an offset of
       0x10000 (0xA0110000), housing the four BRAM scratchpad arrays.

Control & Status Registers (Base Offset 0x0000) All registers are 32-bit and require
4-byte aligned accesses.
   ●​ 0x0000 CTRL (Write-only): Controls execution. Writing bit 0
      (DOT_CTRL_START) launches a computation, while bit 1
      (DOT_CTRL_CLEAR) wipes DONE, ERR, and the interrupt line.
   ●​ 0x0004 STATUS (Read-only): Execution state. Bit 0 indicates BUSY, bit 1
      indicates DONE (sticky), and bit 2 indicates ERR (sticky).
   ●​ 0x0008 NB (Read/Write): Sets the number of 32-element blocks (signed 32-bit),
      clamped hardware-side to a maximum of 152.
   ●​ 0x000C RESULT (Read-only): Holds the final FP32 dot product output as raw
      IEEE-754 bits.
   ●​ 0x0010 IRQ_EN (Read/Write): Enables the hardware interrupt line when DONE is
      set.
   ●​ 0x0014 CYCLES (Read-only): Reports the accelerator clock cycles consumed by
      the last computation.
   ●​ 0x001C ID (Read-only): Holds a static probe check value of 0xD07A0001.

Scratchpad Buffer Layout (Base Offset 0x10000) The inputs must be strictly
de-interleaved by the software HAL before being written. The four arrays are separated
by gaps, and any bus access crossing an array boundary triggers a TLM address error.

   ●​ 0x10000 XQ (Read/Write): Holds the 8-bit weights for the X vector (capacity:
      4864 bytes).
   ●​ 0x12000 YQ (Read/Write): Holds the 8-bit weights for the Y vector (capacity:
      4864 bytes).
   ●​ 0x14000 XD (Read/Write): Holds the FP16 scales for the X vector, stored as raw
      16-bit little-endian values (capacity: 304 bytes).
   ●​ 0x15000 YD (Read/Write): Holds the FP16 scales for the Y vector (capacity: 304
      bytes).
The Typical Software Sequence For every dot product computed, the software driver
executes the following sequence:

   1.​ Write IRQ_EN = 1 (if utilizing interrupts).
   2.​ Write the de-interleaved payload to the XQ, YQ, XD, and YD scratchpads (writing
       only the required byte length).
   3.​ Write the total block count to the NB register.
   4.​ Write CTRL = START to initiate execution.
   5.​ Wait for completion, either by sleeping until the interrupt fires, or by actively
       polling STATUS.DONE.
   6.​ Read the raw floating-point output from RESULT and the latency metrics from
       CYCLES.
   7.​ Write CTRL = CLEAR to drop the interrupt line and clear the DONE status,
       preparing the accelerator for the next batch.

llama.cpp Integration:
        The accelerator hooks into llama.cpp at the GGML tensor-computation library
level. The accelerator is injected at the lowest mathematical level which is the Q8_0
dot-product dispatch point. This allows the hardware to handle the heavy matrix math
while the rest of the neural network execution remains in software. In ggml-cpu.c, the
default Q8_0 dot-product function pointer is overridden by a custom wrapper
(lab3_vec_dot_q8_0_q8_0) when the LAB3_DOT_HAL macro is defined.
        If a dot product exceeds the hardware maximum of 152 blocks (4,864 elements) or
uses an unsupported shape, the wrapper safely routes it to the original CPU
implementation. However, if a supported hardware request fails at the driver level, the
wrapper aborts the application immediately to ensure hardware failures are visibly
caught, rather than silently falling back to the CPU.
        The integration is injected into the build using the SOC_DOT_HAL_DIR CMake
flag, which includes part4/integration/ggml.cmake to compile the HAL and wrapper into
the CPU library.
When a dot product is requested, the wrapper inspects the matrix shape and length. If the
inputs are supported, it passes them to the HAL function dot_hal_dot_q8_0. Once the
HAL returns a result, the wrapper writes that single float into GGML's requested output
memory pointer so model generation can continue.


Hardware Abstraction Layer (HAL)

The HAL (dot_hal.c) operates in user space as part of the compiled application, isolating
device access details from GGML. Its core responsibility is to translate the application's
internal tensor data formats into hardware-compatible structures and manage the lifecycle
of requests to the kernel driver, keeping the rest of the application completely unaware of
device access details.

llama.cpp natively stores Q8_0 vectors in 34-byte interleaved blocks containing an FP16
scale followed by 32 signed 8-bit values. The accelerator hardware cannot parse these
packed interleaved structs. It requires the quantized values and their floating-point scales
to be supplied in strictly separate memory arrays.

Because the hardware requires separate arrays, the HAL de-interleaves these blocks into
four distinct contiguous buffers (XQ, XD, YQ, YD). This is done entirely without
dequantizing the values into software floats. The HAL computes the block count (NB) by
dividing the vector element count by 32, enforcing the 152-block maximum before
passing the request to the driver.

This reorganization is purely a memory-shuffling operation. The HAL intentionally
preserves the raw FP16 bit representations and 8-bit quantized integers, performing no
dequantization or software dot-product math itself.



Linux Kernel Driver

The Linux driver (dot_accel_drv.ko) executes entirely in kernel space on the ARM
processor, serving as the exclusive owner of the accelerator's control registers and input
memories. Managing the complete hardware transaction by loading inputs, starting
computation, waiting for completion, and retrieving results, the driver keeps all hardware
access and synchronization centralized in one place.
        Upon loading, the driver matches the ece382m,dotaccel compatible string in the
device tree, maps the control registers (0xA0100000, 256 bytes) and scratchpads
(0xA0110000, 24 KB), and verifies the 0xD07A0001 hardware ID. The hardware
contains only one set of input scratchpads. To prevent memory corruption from
multi-threaded applications, the driver serializes all hardware accesses using a mutex,
ensuring only one dot-product transaction occurs at a time. The driver implements a
timeout of approximately one second in guest Linux time. It does not attempt hardware
retries. If a timeout occurs, or if the hardware reports an ERR state, the driver fails the
request. The driver uses Linux I/O accessors to read and write device memory, ensuring
that all input writes are aligned to 32-bit boundaries. Scale data (FP16) is padded when
necessary to avoid unaligned ARM device-memory accesses.

Application - HAL Interface

       The GGML wrapper invokes the HAL through a standard C function call
(dot_hal_dot_q8_0). The HAL rearranges the data and sends the indication to the driver.
It forwards the accelerator's final output by taking it from the driver and transferring it
back to the application by placing this directly into GGML's expected output location.

HAL - Kernel Driver Interface

        The HAL communicates with the driver exclusively through the /dev/dot_accel
device file via ioctl system calls. The HAL first issues this ioctl to validate the driver's
reported identity and block capacities, catching configuration mismatches before any data
is sent. For each dot product, the HAL passes a request structure containing the block
count and user-space pointers to the four de-interleaved arrays. This is a blocking call.
The HAL thread sleeps while the driver takes over the full hardware lifecycle (copying
inputs, starting hardware, and waiting for completion). Once the driver finishes, it
populates the request structure with the FP32 result bits and hardware cycle counts,
which the HAL then extracts.
Hardware Communication Protocol (Driver - SystemC Model)

The communication boundary between the driver in QEMU and the SystemC hardware
model is bridged by Xilinx's remote-port framework, translating ARM MMIO accesses
into TLM-2.0 transactions over a Unix socket.



   a)​ Programmed Data Transfer (MMIO)

             The accelerator acts as a pure memory-mapped bus slave without DMA
      capabilities. The driver copies the input vectors from user space directly into the
      hardware's mapped scratchpad memories (XQ, YQ, XD, YD) using 32-bit aligned
      MMIO writes (writel/memcpy_toio).

   b)​ Hardware Execution Handshake

              The driver writes DOT_CTRL_CLEAR to the CTRL register to wipe any
      previous DONE or ERR states and disable previous interrupts. The driver writes
      the total number of blocks to the NB register. The driver issues the START
      command to the CTRL register, signaling to the SystemC model that inputs are
      ready.

3.3 Completion and Acknowledgement
      The driver supports a level-sensitive interrupt mechanism routed through PL2PS
IRQ 5 (GIC ID 126 / SPI 94). The driver sleeps while the hardware executes. When the
hardware sets the DONE status, it asserts the interrupt. The driver's interrupt handler
wakes up, acknowledges the device by writing CTRL = CLEAR (which instantly
deasserts the hardware interrupt line), and wakes the blocked thread.

       Alternatively, the driver can operate in polling mode, repeatedly reading the
STATUS register until the DONE bit goes high. After waking up or detecting DONE, the
driver reads the RESULT and CYCLES registers, completes the ioctl transaction, and
releases the driver mutex for the next application request.
