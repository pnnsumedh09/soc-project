Part 4 - Creating Standalone, Synthesizable Code
The standalone dot product function dot_q8_0 was created for Part 4 and
here are the main changes compared to Part 3:

  ●​ The original software interface was simplified to accept the number of
     blocks and four typed input arrays.
  ●​ The interleaved Q8_0 blocks were separated into quantized-value
     arrays (xq, yq) and scale arrays (xd, yd).
  ●​ Fixed maximum sizes of 4,864 elements and 152 blocks were defined
     and inputs larger than this limit were clamped.
  ●​ The Vitis half type and a fixed integer-based FP16-to-FP32
     conversion were used to preserve normal and denormal FP16 values.
  ●​ The outer and inner loops were labeled BLOCK_LOOP and
     ELEM_LOOP for later optimization.

The following HLS pragmas were added:
#pragma HLS INTERFACE mode=bram port=xq depth=4864
#pragma HLS INTERFACE mode=bram port=yq depth=4864
#pragma HLS INTERFACE mode=bram port=xd depth=152
#pragma HLS INTERFACE mode=bram port=yd depth=152
#pragma HLS LOOP_TRIPCOUNT min=28 max=152

The BRAM pragmas create memory interfaces for the quantized values
and FP16 scales. The trip-count pragma gives Vitis the expected range of
28 to 152 blocks, corresponding to vectors containing 896 to 4,864
elements, so that latency can be estimated at both bounds.

Handling FP16 Denormal Values
Vitis floating-point IP flushes denormalized FP16 values to zero. This
affected tests in which the scale factors for both input vectors were
denormal. In these cases, the hardware result became zero while the
reference result remained nonzero, producing a relative error of:
Before applying a workaround, 13 of the 51 tests failed, with a maximum
absolute error of (6.683066 * 10^(-5)) and a maximum relative error of
100%. The absolute error remained small because the affected
denormal-scale results were themselves very small.




To preserve denormal values, we implemented a workaround. When a
denormal is detected, its mantissa is shifted until the leading one reaches
the implicit-bit position, and the FP32 exponent is adjusted accordingly. A
fixed four-step leading-zero count is used instead of a data-dependent
loop, keeping the conversion synthesizable.




After applying this workaround, all 51 tests passed bit-exactly and both the
maximum absolute and relative errors were reduced to zero.

Compared with the floating-point implementation, which produced zero
absolute and relative error, the fixed-point implementation introduced a
maximum relative error of 5.62% while consuming more DSPs, LUTs, and
FFs. Fixed-point arithmetic is therefore hardware-efficient only when the
data has a relatively narrow dynamic range. For this llama.cpp workload,
supporting the extreme input range requires very wide fixed-point values,
making the resulting design less area-efficient than the floating-point
implementation.
Part 6 - Optimizing the Design
To optimize our design, we explored the following four optimizations
provided by Vitis HLS:

   ●​ Loop Unrolling
   ●​ Pipelining
   ●​ Array Partitioning
   ●​ Array Reshaping

In our design, BLOCK_LOOP is the outer loop that iterates over the Q8_0
blocks, while ELEM_LOOP is the inner loop that computes the dot product
within each block. These loop names are references in further sections.

Since the number of blocks is provided at runtime, we provided Vitis with an
expected range of 28 to 152 iterations, corresponding to 896 and 4,864
elements. The following tables report latency at both bounds to show how
each optimization scales with input length.

Here is our analysis of each optimization and its effect on performance:

1. Loop Unrolling
Loop unrolling was applied to ELEM_LOOP. We evaluated three
configurations with unroll factors of 8, 16, and 32.

These commands were used for the unroll factor 8 configuration:

config_compile -pipeline_loops 0
set_directive_unroll -factor 8 "dot_q8_0/ELEM_LOOP"

The same commands were used for the other two configurations by
changing the argument from 8 to 16 and 32. Since the Vitis default
configuration enables pipelining on the outer loop, it unrolls the inner loop
completely. The config_compile -pipeline_loops 0 command disables
automatic loop pipelining, allowing us to analyse the effect of unrolling.
An unroll factor of 8 executes eight iterations of ELEM_LOOP in parallel,
while a factor of 16 doubles that parallelism. Since the loop has 32
iterations, a factor of 32 fully unrolls it, allowing all element wise
multiplications to be executed in parallel. The actual performance
improvement still depends on the available memory bandwidth.

2. Pipelining
Pipelining was evaluated using the default Vitis optimization configuration.
Unlike the unrolling configurations, automatic loop pipelining was not
disabled. With its default settings, Vitis automatically pipelines
BLOCK_LOOP and fully unrolls ELEM_LOOP.
The resulting outer-loop initiation interval was 16 cycles. Pipelining allows
operations of consecutive Q8_0 blocks to overlap rather than waiting for all
operations associated with one block to finish before starting the next.

3. Array Partitioning
The arrays are initially mapped to BRAM interfaces in dot_q8_0.cpp:

#pragma HLS INTERFACE mode=bram port=xq depth=4864
#pragma HLS INTERFACE mode=bram port=yq depth=4864
#pragma HLS INTERFACE mode=bram port=xd depth=152
#pragma HLS INTERFACE mode=bram port=yd depth=152

The quantized arrays xq and yq require multiple reads per cycle to supply
the unrolled datapath. By default, each array provides two read ports. To
increase the available memory bandwidth, each quantized array was
cyclically partitioned into two banks.
The following directives were added to directives.tcl:

set_directive_array_partition \
  -type cyclic -factor 2 -dim 1 \
  "dot_q8_0" xq

set_directive_array_partition \
  -type cyclic -factor 2 -dim 1 \
  "dot_q8_0" yq

A cyclic partition factor of two distributes alternating array elements
between two memory banks. Since each bank can provide two ports, the
accelerator receives four aggregate read ports for xq and four for yq.

Array-partitioning results

Doubling the available read bandwidth reduced the initiation interval from
16 to 8. As a result, the latency was reduced by approximately half for both
evaluated vector lengths.

Increasing the number of memory banks should normally increase BRAM
usage and total area. However, this increase is not visible in the reported
BRAM count because the current synthesis scope treats these arrays as
external BRAM interfaces.
4. Array Reshaping
Array reshaping changes the width of each memory word so that several
adjacent int8_t elements can be read in one access. We evaluated three
configurations with reshape factors of 8, 16, and 32.

The following directive was used for the reshape factor 8 configuration:

set_directive_array_reshape -type cyclic -factor 8 -dim 1 "dot_q8_0" xq
set_directive_array_reshape -type cyclic -factor 8 -dim 1 "dot_q8_0" yq

The same directives were used for the other two configurations by
changing the factor argument from 8 to 16 and 32.

A reshape factor of 8 packs eight signed 8-bit elements into 64-bit memory
word. Factors of 16 and 32 produce 128-bit and 256-bit words, respectively.
The factor 32 configuration therefore provides all 32 quantized values
associated with one Q8_0 block through a wide memory interface.

Overall Performance and Area Comparison




The performance graph shows how loop unrolling, pipelining, array
partitioning and array reshaping affect latency. By default, Vitis pipelines
the outer loop and fully unrolls the inner loop. Building on this configuration,
reshaping the arrays by a factor of eight produced the lowest latency. We
refer to this combination as the Optimized Reshape-8 configuration
throughout the following analysis.

The area graph illustrates the trade-off between performance and hardware
cost. As performance improved through these optimizations, LUT and FF
usage generally increased because additional parallel hardware and
control logic were required. Among the configurations evaluated, the
Optimized Reshape-8 configuration provided the best balance between
performance and area.

All configurations in this comparison were synthesized using a target clock
period of 10 ns. For the clock-optimization analysis, we therefore select the
Optimized Reshape-8 configuration and evaluate it across a range of target
clock periods.

period, corresponding to 111.1 MHz, provides the lowest execution time for
both input sizes while maintaining positive slack.
